A Git host with no server underneath.

GitBucket is a GitHub-style Git host that runs as a single Go binary on Cloud Run. Objects live in Cloud Storage, refs in Firestore — no VMs, no disks, no Git server to babysit. Between pushes, it simply isn't running.

architecture

Three managed services. Zero infrastructure.

Every Git request materializes your repo on demand, runs real git-http-backend against it, then syncs everything back to durable storage. The instance can vanish; your history can't.

compute

▸ Cloud Run

One Go binary serves the API, the web UI, and Git Smart HTTP. Scales with your pushes — including down to zero.

objects

▸ Cloud Storage

Loose objects, pack-files, and LFS blobs — content-addressed, immutable, and priced like the commodity storage it is.

state

▸ Firestore

Users, tokens, refs, pull requests, and locks — every branch update is an ACID transaction, not a file rename.

features

Everything a small team pushes to.

Real Git over HTTPS

clone, push, pull, fetch via Git Smart HTTP, backed by stock git-http-backend — full protocol compatibility, no custom client.

Pull requests, properly

Split-view diffs with a file tree, inline comments, approve / request-changes reviews, and one-click merge.

Branch protection

Pattern rules with push and merge allowlists, required approvals, force-push and deletion blocking — plus CODEOWNERS reviewer auto-assignment.

Git LFS included

Large files land in the same bucket as your objects. No add-on, no separate quota to manage.

CI on every commit

Cloud Build integration puts pass/fail badges on commits and PRs, with build logs streamed live in the UI.

Locked-down access

Google sign-in with TOTP two-factor for the web; scoped gb_pat_… tokens for the CLI. Private repos with per-repo collaborators.

under the hood

What actually happens when you push

01

Your push hits Cloud Run

Git Smart HTTP over HTTPS, authenticated with your username and a personal access token. A container spins up if none is running.

02

The repo materializes

Objects and refs stream out of Cloud Storage and Firestore into a scratch directory, and stock git-http-backend processes your pack — the same binary GitHub's protocol grew up on.

03

Protection rules run

Proposed ref updates are checked against branch-protection rules — allowlists, required approvals, force-push blocks — before anything becomes canonical.

04

Everything syncs back

New objects upload to Cloud Storage; refs commit to Firestore in a transaction. The instance is now disposable — and if nobody pushes again, it scales to zero.
